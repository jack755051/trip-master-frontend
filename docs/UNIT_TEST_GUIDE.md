# 🧪 單元測試核心指南 (Unit Testing Core Guide)

## 1. 核心哲學：測試「行為」而非「行數」

單元測試不是為了覆蓋代碼，而是為了驗證 **「契約 (Contract)」**。

- **誤區**：一個 Function 寫一個測試，測試內部實作。
- **正解**：一個 Function 根據不同輸入產生多種「行為」，每個行為都是一個測試。

## 2. 測試建構模式：AAA 模式

所有測試案例應遵循 AAA 結構，確保可讀性：

1. **Arrange (安排)**：準備資料、Mock 環境。
2. **Act (執行)**：呼叫被測函數。
3. **Assert (斷言)**：驗證輸出是否符合預期。

## 3. 測試選型準則 (What to test?)

我們將測試對象分為三個等級，優先序如下：

### A. 核心邏輯層 (Services / Libs) - **優先度：最高**

- **特徵**：純函數 (Pure Functions)、計算邏輯、數據轉換。
- **核心**：確保 $Input \rightarrow Output$ 的決定性（相同的輸入永遠得到相同的輸出）。
- **關鍵點**：必須模擬 (Mock) 時間與網路環境。

### B. 狀態與副作用層 (Hooks) - **優先度：中**

- **特徵**：涉及 React 狀態流轉、API 呼叫觸發。
- **核心**：驗證「當狀態改變時，Hook 的行為是否正確」。

### C. 展示與交互層 (Components) - **優先度：低**

- **特徵**：UI 渲染、點擊事件。
- **核心**：只測核心交互路徑，不測樣式 (CSS)。

## 4. 撰寫原則 (Best Practices)

- **冪等性**：測試結果不應受執行順序、時間或次數影響。
- **描述性命名**：`it("應該在輸入為空時回傳預設值")` 優於 `it("test_empty_case")`。
- **邊界測試**：除了正確流程，必須包含 `null`、`undefined`、極端大數值等測試。

## 5. 專業守門員：@ts-expect-error

在測試非法類型輸入時，使用 `@ts-expect-error`。

- **原因**：這能確保當我們刻意傳入錯誤參數時，編譯器會報錯；如果未來代碼變更導致傳入此參數不再報錯，測試會提醒我們「契約已變」。
